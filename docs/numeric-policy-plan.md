# Development Plan: Numeric Precision Policy Matrix (v16)

A focused implementation of mixed-precision arithmetic for liq-ta, keeping `f32` arrays for throughput while using `f64` selectively for numerical stability.

---

## Executive Summary

**Goal**: Implement a numeric policy that maintains SIMD throughput and cache efficiency (`f32` arrays) while preventing precision loss in sensitive operations (`f64` state/accumulators).

**Key Principle**: "f64 for state, f32 for storage" - avoid `f64` intermediate arrays.

**Core Strategy**: Use **f64 accumulators with sum-of-squares variance** (not Welford buffer). The f64 precision largely mitigates catastrophic cancellation that sum-of-squares suffers in f32. This maintains O(n) performance while improving precision.

**Scope**: Four focused areas:
1. F64 accumulators for rolling sums (SMA, variance numerator/denominator)
2. F64 for sensitive divisions (small denominators)
3. F64 for cumulative indicators (VWAP, OBV, AD)
4. F64 for Wilder smoothing state (RSI)

---

## Design Principles

This section establishes constraints to prevent complexity creep:

### Single Responsibility (SOLID)
- **All PrecisionMode logic lives in `precision.rs`**: enum, TLS, env/feature initialization, `set_precision_mode()`, `with_precision_mode()`, `current_precision_mode()`
- Indicators call `current_precision_mode()` — they don't implement mode logic
- Accumulators live in `kernels/accumulators.rs` — separate from mode selection

### Don't Repeat Yourself (DRY)
- **Error Tolerance Specification** (below) is the single source of truth for tolerance values
- Tasks and tests reference the table, not restate tolerances
- Golden test strategy references the tolerance table

### Keep It Simple (KISS)
- **Precision Mode Configuration** (below) is the single source for mode selection logic
- Other sections reference it rather than re-explaining precedence, TLS, or benchmark guidance
- One code block per concept; reference it elsewhere

## Error Tolerance Specification

All precision improvements must meet these concrete tolerances when comparing f32 High mode against pure f64 reference:

| Indicator | Relative Tol | Absolute Tol | Rule | Rationale |
|-----------|--------------|--------------|------|-----------|
| RSI, Stochastic %K/%D, Williams %R, MFI | — | 0.01 | abs | Bounded 0-100 or -100-0 |
| SMA, Bollinger bands/middle/upper/lower | 1e-5 | 1e-7 | hybrid | Price-scale output |
| VWAP | 1e-5 | 1e-7 | hybrid | Ratio of cumulative sums |
| OBV, AD | 1e-4 | 1.0 | hybrid | Unbounded cumulative sum |
| VAR, STDDEV | 1e-5 | 1e-10 | hybrid | Squared values; abs for near-zero |
| CCI | 1e-4 | 0.1 | hybrid | Unbounded, typically ±200 |
| CORREL | 1e-5 | 1e-6 | hybrid | Bounded -1..+1 |
| BETA | 1e-4 | 0.01 | hybrid | Unbounded slope coefficient |
| LINEARREG, LINEARREG_SLOPE, LINEARREG_INTERCEPT, LINEARREG_ANGLE | 1e-5 | 1e-7 | hybrid | Price-scale or angle output |
| ROC, ROCP, ROCR, ROCR100 | 1e-5 | 1e-7 | hybrid | Ratio/percentage output |

**Tolerance Rules** (implemented by tolerance helpers in test code):
- **abs**: `diff <= abs_tol` — for bounded indicators where relative error is meaningless
- **hybrid**: `diff <= abs_tol || diff <= rel_tol * |expected|` — for unbounded/price-scale indicators

**Tolerance Helpers** (canonical implementation):
```rust
/// For bounded indicators (RSI, Stochastic, Williams %R, MFI) - abs rule
fn within_abs(actual: f64, expected: f64, abs_tol: f64) -> bool {
    (actual - expected).abs() <= abs_tol
}

/// For unbounded/price-scale indicators - hybrid rule
fn within_hybrid(actual: f64, expected: f64, rel_tol: f64, abs_tol: f64) -> bool {
    let diff = (actual - expected).abs();
    diff <= abs_tol || diff <= rel_tol * expected.abs()
}
```

**EMA Note**: EMA is excluded from this table because EMA precision changes are deferred (see Deferred Items). EMA uses native-type accumulation in both High and Fast modes.

**Note on RSI**: Previous draft specified 0.001 which is too tight for Wilder smoothing (EMA-like). RSI accumulates small errors over time; 0.01 is realistic.

**Measurement Protocol**:
- Generate synthetic data: linear, sinusoidal, random walk, extreme values
- Compute with f32 input → f64 internal → f32 output
- Compare against pure f64 computation
- Report max error, mean error, RMS error

**Reproducibility Specification**:
- Random seed: `0xFA57_7A00` (4200036864 decimal, mnemonic: "FAST-TA-00")
- Random walk: 10,000 bars, starting price 100.0, volatility 2% daily
- Extreme values: includes ±1e6, ±1e-6, clustered small values
- Near-constant data: base=1000.0, noise < 1e-4 (triggers cancellation)
- Datasets generated by Task 0.4 and committed to `crates/liq-ta/test-data/precision/`

## Precision Mode Configuration

This is the **single source of truth** for all mode selection logic. All code lives in `precision.rs` (per Design Principles).

### PrecisionMode Enum

```rust
/// PrecisionMode with explicit u8 representation for atomic storage
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
#[repr(u8)]
pub enum PrecisionMode {
    #[default]
    High = 0,
    Fast = 1,
}

impl PrecisionMode {
    fn from_u8(v: u8) -> Self {
        match v { 1 => PrecisionMode::Fast, _ => PrecisionMode::High }
    }
}
```

### Configuration Precedence

(highest to lowest):
1. **TLS override** via `with_precision_mode()` — test-only, bypasses all other config
2. **Runtime** `set_precision_mode()` — sets global mode, prevents env/feature override
3. **Environment variable** `LIQ_TA_PRECISION=fast|high` — read once at initialization
4. **Cargo feature** `precision-fast` — compile-time default if no env var
5. **Built-in default**: `PrecisionMode::High`

### Internal State

```rust
static INIT: Once = Once::new();
static GLOBAL_MODE: AtomicU8 = AtomicU8::new(PrecisionMode::High as u8);
static MANUAL_OVERRIDE: AtomicBool = AtomicBool::new(false);

thread_local! {
    static THREAD_OVERRIDE: Cell<Option<PrecisionMode>> = Cell::new(None);
}
```

### Core Functions

```rust
/// Called by current_precision_mode() to apply env/feature defaults once
fn ensure_initialized() {
    INIT.call_once(|| {
        if MANUAL_OVERRIDE.load(Ordering::Relaxed) { return; }
        if let Ok(val) = std::env::var("LIQ_TA_PRECISION") {
            match val.to_lowercase().as_str() {
                "fast" => GLOBAL_MODE.store(PrecisionMode::Fast as u8, Ordering::Relaxed),
                "high" => GLOBAL_MODE.store(PrecisionMode::High as u8, Ordering::Relaxed),
                _ => {}
            }
            return;
        }
        #[cfg(feature = "precision-fast")]
        GLOBAL_MODE.store(PrecisionMode::Fast as u8, Ordering::Relaxed);
    });
}

pub fn set_precision_mode(mode: PrecisionMode) {
    MANUAL_OVERRIDE.store(true, Ordering::Relaxed);
    GLOBAL_MODE.store(mode as u8, Ordering::Relaxed);
}

#[inline]
pub fn current_precision_mode() -> PrecisionMode {
    if let Some(mode) = THREAD_OVERRIDE.with(|c| c.get()) { return mode; }
    ensure_initialized();
    PrecisionMode::from_u8(GLOBAL_MODE.load(Ordering::Relaxed))
}

/// RAII guard for panic-safe TLS restore
struct PrecisionModeGuard { prev: Option<PrecisionMode> }
impl Drop for PrecisionModeGuard {
    fn drop(&mut self) { THREAD_OVERRIDE.with(|cell| cell.set(self.prev)); }
}

pub fn with_precision_mode<F, R>(mode: PrecisionMode, f: F) -> R
where F: FnOnce() -> R {
    THREAD_OVERRIDE.with(|cell| {
        let prev = cell.get();
        cell.set(Some(mode));
        let _guard = PrecisionModeGuard { prev };
        f()
    })
}
```

### Behavior Matrix

| Input Type | PrecisionMode::High | PrecisionMode::Fast |
|------------|---------------------|---------------------|
| f32 | f64 accumulators, f32 output | f32 accumulators (original) |
| f64 | f64 accumulators (no change) | f64 accumulators (no change) |

### Usage Guidance

**Production** (one of):
```rust
liq_ta::set_precision_mode(PrecisionMode::High);  // runtime
LIQ_TA_PRECISION=fast cargo run                   // env var
liq-ta = { features = ["precision-fast"] }        // feature
```

**Tests** — use `with_precision_mode()` for isolation:
```rust
#[test]
fn test_sma_high_precision() {
    with_precision_mode(PrecisionMode::High, || { /* ... */ });
}
```

**Benchmarks** — use `set_precision_mode()` to measure production path:
```rust
set_precision_mode(PrecisionMode::Fast);
group.bench_function("fast", |b| b.iter(|| sma(&data, 20)));
```

### Limitations

- **TLS does not propagate** to child threads. For multi-threaded tests, use `set_precision_mode()` before spawning or have each thread call `with_precision_mode()`.
- **TLS bypasses initialization** — by design, tests control their own mode.
- **CI env var caveat**: tests using `with_precision_mode()` ignore `LIQ_TA_PRECISION`. Separate test modules if needed.

## Algorithm Selection: Variance

### Why Sum-of-Squares with f64 (Not Welford Buffer)

**Problem with Welford buffer recomputation**: O(n × period) time complexity. For Bollinger with period=200, this is ~200x slower than O(n) rolling algorithm.

**Solution**: Keep the existing sum-of-squares algorithm but use f64 accumulators:

```rust
// Current (f32, has cancellation issues):
let var = (sum_sq / n) - (sum / n).powi(2);  // E[X²] - E[X]²

// Improved (f64 accumulators, cancellation largely mitigated):
let sum_f64: f64 = ...;      // rolling sum in f64
let sum_sq_f64: f64 = ...;   // rolling sum of squares in f64
let mean = sum_f64 / n as f64;
let var = (sum_sq_f64 / n as f64) - mean * mean;
// See "Zero-Variance Clamp Policy" below
```

### Zero-Variance Clamp Policy

**Problem**: Sum-of-squares can compute negative variance due to floating-point error, and true zero variance causes div-by-zero in stddev.

**Policy**: Variance clamping is **mandatory** in variance accumulators:

```rust
// In RollingVarianceF64::variance()
let raw_var = (self.sum_sq / n) - (self.sum / n).powi(2);
raw_var.max(0.0)  // Clamp to zero, not epsilon
```

**Rationale**:
- Clamp to `0.0`, not `f64::EPSILON` - epsilon creates false signal where none exists
- Downstream indicators (Bollinger bands) handle zero variance explicitly:
  - Zero variance → bands collapse to mean (correct behavior for constant data)
  - Division by stddev uses `if stddev == 0.0 { ... }` guard, not epsilon padding
- This is clearer than "magic" epsilon that masks the true data condition

**Compatibility Note (Behavior Change)**:
- **Before**: Constant inputs could produce tiny non-zero variance due to floating-point noise
- **After**: Constant inputs produce exactly zero variance (and zero stddev)
- **Impact**: Bollinger bands for constant data will collapse to the mean line (upper = middle = lower)
- This is **correct mathematical behavior** but may affect downstream code that assumed non-zero stddev
- Fast mode preserves original behavior for comparison

**Why this works**: Catastrophic cancellation in `E[X²] - E[X]²` occurs when both terms are large and nearly equal. With f64:
- 15-16 significant digits vs 7-8 for f32
- Cancellation that loses 8 digits in f32 still leaves 7+ digits in f64
- Real market data rarely has the extreme uniformity that triggers worst-case cancellation

**Tradeoff accepted**: Not as numerically stable as Welford, but O(n) and much faster. Users needing maximum stability should use f64 input type directly.

**Optional Welford**: If users request it, add `bollinger_welford()` variant that uses buffer-based Welford for period ≤ 100. This is opt-in, not default.

### Task 2.3: Migrate Stochastic/Williams %R to F64 Division

**Type**: Implement

**Description**: Upcast to f64 before computing `(close - low) / (high - low)`.

**Acceptance Criteria**:
- [ ] Use proper generic conversion with zero-range guard:
  ```rust
  // Stochastic (0..100 range)
  let high_f64 = high.to_f64().unwrap_or(f64::NAN);
  let low_f64 = low.to_f64().unwrap_or(f64::NAN);
  let close_f64 = close.to_f64().unwrap_or(f64::NAN);
  let range = high_f64 - low_f64;
  if range == 0.0 {
      return T::from_f64(50.0).unwrap_or(T::nan());  // Stochastic: midpoint of 0..100
  }
  let position = close_f64 - low_f64;
  let result = T::from_f64(100.0 * position / range).unwrap_or(T::nan());

  // Williams %R (-100..0 range) - different zero-range value
  if range == 0.0 {
      return T::from_f64(-50.0).unwrap_or(T::nan());  // Williams: midpoint of -100..0
  }
  ```
- [ ] Stochastic zero-range (high == low) returns 50.0 (midpoint of 0..100)

## Appendix: Integer Volume Handling

For indicators that use volume (VWAP, OBV, AD, MFI), the accumulators accept any type that implements `Into<f64>`:

```rust
// Supported volume types:
let sum_v: f64 = 0.0;
sum_v += (volume_u32 as f64);   // u32
sum_v += (volume_u64 as f64);   // u64 (precision loss above 2^53)
sum_v += (volume_f32 as f64);   // f32
sum_v += volume_f64;            // f64

// Product sum for VWAP:
sum_pv += price.to_f64().unwrap_or(f64::NAN) * (volume as f64);
```

**u64 Precision Loss Behavior**:
- u64 values above 2^53 (9,007,199,254,740,992) will lose precision when cast to f64
- This is acceptable because:
  - Real-world volume data rarely exceeds 2^53 shares
  - Even if precision is lost, it's in the least significant bits
- **Explicit behavior**: No warning or error is produced; the cast proceeds silently
- **Recommendation**: If exact integer arithmetic above 2^53 is critical, track cumulative volume externally using integer types (u128, i128) and only convert to f64 for indicator input. Note: the liq-ta API accepts types implementing `Into<f64>`, so very large integers must be explicitly cast with `volume as f64`.
